# 图片格式兼容

记录日期：2026-10-21。本文说明当前开发候选的第一批格式扩展、保留的限制和后续发布待办；源码实现、运行验证与安装包发布分别记录。

## 第一批：BMP、ICO 与动画打开效率

当前程序支持 JPEG、PNG、GIF、WebP、BMP、ICO 六种查看格式。打开对话框、拖入文件、同目录浏览、格式筛选和剪贴板单个本地文件路径均接入 BMP/ICO。文件内容探测决定实际解码格式；扩展名用于目录枚举和格式筛选，改扩展名不会把不支持的内容变成支持的图像。

BMP/ICO 通过现有后台加载、取消、显示准备、预算准入和缩略图管线处理。文件数量、输入体积、像素数和路径限制没有因格式扩展而放宽；损坏、越界或不支持的编码返回明确错误。

| 格式 | 查看范围 | 复制与导出 |
| --- | --- | --- |
| JPEG / PNG | 静态图像，沿用现有方向、色彩和透明度处理 | 当前图像可复制，导出 PNG/JPEG 新副本 |
| GIF / WebP | 静态图像和有界动画播放；可播放/暂停、下一帧、从头播放 | 复制当前静态帧；编辑或导出先明确提取当前帧为静态副本 |
| BMP | 由当前解码器支持的静态位图编码；保留既有安全检查 | 当前图像可复制，导出 PNG/JPEG 新副本，不编码 BMP |
| ICO | PNG/DIB 内部图像，默认选择一个条目，支持手动切换 | 针对选中的内部图像复制、贴图或导出 PNG/JPEG，不编码 ICO 容器 |

## ICO 内部尺寸

打开 ICO 时优先选择像素面积最大的图像；面积相同优先更高位深，仍相同则取目录中靠前的条目。目录最多 1024 个条目，检查条目数量、范围、尺寸和编码头，像素与 DIB 掩码仍由现有解码器处理。CUR 光标文件不纳入本批支持。

在信息面板顶部、文件名与像素尺寸下方的“图标尺寸”下拉框中选择 ICO 保存的内部图像。选项显示宽、高、位深及条目序号，同尺寸的不同条目也可区分。这是读取容器内的另一张图像，不是对当前图像进行插值缩放。

- 显式切换尺寸走后台加载流程，保留当前画面，准备成功后替换；与继续切图复用一个加载线程，取消过时请求。
- 有未导出修改时，先按既有流程选择导出后继续、放弃后继续或取消；取消会保留当前图像和修改。
- F5 按宽高与位深保留选择，不依赖旧目录索引；外部重排条目仍匹配原尺寸。原尺寸被删除时选择当前默认最大项；若内容被替换为其他受支持格式，则正常按内容重新载入。菜单中的显式索引选择仍严格报错，不隐性回退。
- 复制、贴图和 PNG/JPEG 导出针对当前选中的内部图像及其当前编辑结果；不会把多个尺寸打包到输出中。
- ICO 选择为当前会话状态，重新从目录打开该文件仍按默认规则选择。

## GIF/WebP 动画

已有播放、暂停、下一帧和从头播放，遵循文件循环信息。本轮针对打开与接续播放减少两处重复工作：

1. GIF 静态/动画探测跳过压缩像素子块，读取帧头以判断是否存在第二帧；真正显示路径仍验证首帧像素，避免探测阶段先完整解码一次首帧。
2. 动画 worker 接续已显示的首帧时，仍恢复正确的合成与 disposal 状态，但跳过首帧重复的 ICC 转换和显示像素准备，再继续读取下一帧。

这些是具体路径的重复工作优化，不承诺所有素材都有固定的加速比例，也没有收集或缓存整段动画。损坏像素、帧范围、取消和资源准入仍按原边界检查。

本轮没有倍速、时间轴拖动、上一帧或手动循环模式；独立贴图仍冻结创建时的当前帧，不播放动画。GIF/WebP/APNG 动画编码不在当前导出范围。

## 保留的限制

| 资源 | 当前限制 |
| --- | --- |
| 输入文件 | 64 MiB |
| 静态图像 | 1600 万像素，单边 32768 |
| 动画 | 400 万画布像素，每次遍历最多 2000 帧 |
| 动画合成与预读 | 128 MiB，同时计入全局准入，只保留当前与一个待显示帧 |
| ICO 目录 | 最多 1024 个内部条目，单个条目的解码仍受静态管线限制 |
| 同目录浏览 | 最多扫描 10000 个条目、列出 8000 张图像，路径总量继续受限 |
| 缩略图 | 按需最多缓存 48 张，计入浏览预算 |

768 MiB 全局预算是保守应用准入估算，不是进程、GPU 驱动或第三方解码器的硬沙箱。现有 ICC 转 sRGB、透明度、16 位转 8 位查看副本和无覆盖导出规则继续适用。

## 安装包发布待办

本批程序输入格式已扩展，但默认应用候选和 Explorer 菜单仍登记 `.jpg`、`.jpeg`、`.png`、`.gif`、`.webp`。BMP/ICO 注册留到下一次实际安装包发布时统一验收，不把源码输入支持等同于安装集成已交付。

原因是旧 stable launcher 在正常更新时保持不变，并在调用保留的恢复 helper 前严格校验 integration 快照。现有 schema 1 快照包含五扩展名对应的精确注册值、文本和键集合；直接扩展同一个名单会破坏旧事务校验，改为 schema 2 又无法让旧二进制自动读取新快照。回滚后恢复的旧 launcher 也要能继续启动。

发布时需统一设计并验证：

- 保留 schema 1 的历史精确 profile，让新 helper 能读取旧未完成事务；新 profile 单独声明七扩展的允许值和恢复范围。
- 解决旧 stable launcher 读取新事务、健康启动及回滚终态的问题，再同步 Inno 注册、原生快照和写入白名单。
- 保留旧默认应用与菜单所有权保护，不写 UserChoice，不覆盖外来或被用户修改的注册内容。
- 用同一候选安装包覆盖正常升级、注册写入中断、健康失败回滚、旧版再次启动和卸载保留场景。

本轮没有修改这些安装、注册和恢复协议。

## 后续阶段

| 阶段 | 范围 | 当前状态 |
| --- | --- | --- |
| 第二阶段 | APNG、TIFF；明确 APNG 播放和 TIFF 单页/多页、高位深边界 | 规划，未实现 |
| 第三阶段 | AVIF、HEIC/HEIF；评估解码依赖、打包、色彩及 HDR | 规划，未实现 |
| RAW 快览 | 优先内嵌预览，区分原片尺寸与预览尺寸，明确“导出预览”和无预览状态 | 规划，无 RAW 代码 |
| 完整 RAW 解码 | 按需解码原片，另行评估相机型号、压缩变体、大图与高位深处理 | 后续独立评估 |

RAW 快览不附带曝光、白平衡、降噪等冲印功能，也不把内嵌 JPEG 预览视为完整原片解码。
