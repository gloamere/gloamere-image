# v0.7 product integration recovery addendum (2026-10-10)

This implements the approved design's persistent registry and shortcut preimages; it does not claim whole-install atomicity or Windows acceptance.

* Only a compiled fixed allowlist under current-user, 64-bit registry view is addressed: this product's uninstall key, candidate-handler registrations, Explorer verbs, and the two product discovery values. Shared parents, `UserChoice`, extension defaults and HKLM are never changed. Unknown values/subkeys in exclusive product keys block preparation, because Inno itself recreates its uninstall key.
* Save exact registry type/bytes and absence, exclusive-key existence/owner/DACL, and current/legacy Start Menu shortcut bytes, identities and permissions. Fixed known-folder-derived paths replace journal-supplied arbitrary shortcut paths. Backups remain outside the installation and are verified before mutation.
* Predeclare deterministic registration postimages. After successful authenticated Setup, validate its bounded, product-owned output before sealing exact postimages. Dynamic Inno-generated metadata and `.lnk` bytes cannot be safely guessed before execution; an interrupted unsealed transaction that cannot prove exact ownership is retained for repair. Never adopt a foreign concurrent change during rollback.
* Recovery globally preflights every affected value, key and file, then rechecks immediately before each mutation. Only exact before or known after states may be replaced once postimages are sealed. Before sealing, a separately persisted `mark_write_intent` plus the parent's verified Setup identity/cooperative locks authorizes restoration of already-owned preimages across torn writes; new unsealed effects, unknown names, foreign ownership and complete retargeted shortcuts still block recovery. Read back restored bytes/types/security/existence. Newly created product keys/directories are removed only if empty; never use recursive deletion. Repeated recovery must be idempotent.
* Native Windows APIs perform registry and shell-link inspection. Portable memory-backend tests exercise raw types, absent keys/values, duplicate/tampered records, concurrent foreign changes, repeated recovery and postimage sealing without touching a user's registry.

API: `Snapshot::remove_legacy_shortcut(installation, transaction_directory)` (exact old-link migration after durable begin), `Snapshot::mark_write_intent()` (persist before Setup mutation), `Snapshot::preflight_restore(installation, transaction_directory)` (read-only, before restoring any payload), `Snapshot::capture(installation, transaction_directory, explorer, version)`, `validate(installation, transaction_directory)`, `seal_after(installation, transaction_directory)`, `restore(installation, transaction_directory)`. The parent journal persists the returned snapshot before installer execution and the sealed snapshot before reporting pending health.

References: [Microsoft registry security](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-reggetkeysecurity), [Microsoft shell-link inspection](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishelllinkw-getpath), [Inno uninstall registration implementation](https://raw.githubusercontent.com/jrsoftware/issrc/main/Projects/Src/Setup.Install.pas).

## Implementation verification

The adapter uses `RegOpenKeyExW` with explicit `KEY_WOW64_64KEY` and `REG_OPTION_OPEN_LINK` at every registry path component; registry links are refused. It preserves arbitrary raw value types/bytes, including empty `REG_NONE`, while owner markers and executable commands remain exact, local product checks. `GetSecurityInfo` captures owner/DACL; restoration preserves DACL protection and reads the result back. `SHGetKnownFolderPath(FOLDERID_Programs)` supplies destinations, `IShellLinkW`/`IPersistFile` only read existing links, and `GetUserNameW` predeclares the fresh-install username. No shell-link resolution, save, execution or external scripting is used for inspection.

The portable adapter is explicitly tagged as a fixture, contains no native state and is rejected on Windows. Unit tests use a memory backend with no native registry/Start Menu changes. Isolated Linux tests and Windows MSVC cross-checks cover this source against the project's real storage module plus a minimal platform-interface harness. Native Windows execution and exact installer-version output remain release acceptance requirements, rather than claims established by cross-compilation.

The clean-install path verifies the closest existing current-user-owned directory ancestor without creating `{app}` before the parent publishes the root entry. `remove_legacy_shortcut` requires durable write intent, exact old link bytes/permissions and its owned target; it deletes only that link and an empty group, is idempotent, and keeps unrelated group files.
