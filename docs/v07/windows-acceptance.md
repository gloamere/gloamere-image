# v0.7 Windows acceptance handoff

This is a source candidate, not a Windows-tested release. Do not install over a real user's application, change default associations, or use production keys for these tests. Use a disposable standard-user Windows 10/11 profile or VM and explicit fixture directories. Keep the v0.6 source and test snapshots intact. A cloud API/type check is not native execution evidence.

## Build and identity

1. Verify every source entry against SOURCE-MANIFEST.json and the archive SHA-256. The working snapshot has no invented Git commit. Preserve the source manifest alongside all native results.
2. Use official Rust 1.96+, Visual Studio C++ tools/Windows SDK and the established verified Inno Setup 6.7.3 pipeline. AWS-LC additionally needs its documented native build tooling. No unrecognized binary download or OS warning bypass is part of this handoff.
3. Run scripts/verify.ps1 and scripts/build-release.ps1 in the isolated workspace. Record exact tools, command output and the hashes of stable launcher, runtime UI, provenance worker and Setup. Run Debug and Release tests serially, including ignored budget cases, and validate every PE resource and staged dependency notice.
4. The production updater remains unconfigured. For controlled repository testing, use a separate test build with explicitly reviewed test trust material and a valid HTTPS endpoint. Never embed fixture trust into a production artifact. The debug-only fixture-harness feature deliberately refuses Release builds.

## Functional and recovery matrix

- Fresh per-user bootstrap, then exact owned v0.6-to-v0.7 migration, then a second distinct release with a larger release sequence. Ordinary updates must leave the stable launcher unchanged.
- Chinese/spaced paths, independent launch instances, drag/drop/--open/Explorer/Start-menu entry, narrow windows and 100/125/150/200% DPI. An open request during maintenance must retain its arguments while waiting and give an explicit error if the wait expires.
- Normal clean close permits a ready authorized update; dirty edit, export, any modal, hidden window, logoff/shutdown and other live sessions do not. Closing never terminates another UI, worker or installer. Cancel/pause/disable at check, transfer, validation and ready boundaries must match the displayed state.
- Run exact-parent identity/PID-reuse, helper-ready handshake, simultaneous Setup/uninstall, shared-session worker admission, and first-launch admission races. After healthy commit, run pixel inference and provenance checking before restarting the UI, ensuring inherited health variables do not reject children.
- At each journal boundary interrupt only the isolated test process/VM, then restart through the stable launcher. Verify bootstrap root is restored last; old payload, raw registry types/bytes/absence, shortcut bytes and security descriptors read back exactly. Preserve foreign files and settings/models/manual records. Ambiguous unsealed new effects or pending reboot operations must retain evidence and require repair, never claim a successful rollback.
- Test hash/signature tampering, missing/invalid/different Authenticode signature, unsigned PE under explicit TUF-only policy, expired/rolled-back metadata, clock rollback, revoked/quarantined releases, target replacement, path traversal, junction and writable-parent swaps, truncated download, resume ETag changes and low disk. Respect Windows SmartScreen/UAC/AV protections. Test browser/Explorer-downloaded marked EXEs separately from internally downloaded EXEs: the current custom downloader neither invokes Attachment Services nor creates Zone.Identifier. Record actual prompt/block behavior under SmartScreen, Defender, WDAC and UAC; never strip an existing zone stream, run Unblock-File or disable protections. No zero-prompt outcome is promised.
- Commit only after the candidate's actual UI renders, decodes the embedded fixture, reads compatible settings and receives the expected offline provenance-worker protocol/version. Check installed sequence bookkeeping, one-time completion notice and failed-release quarantine after rollback.
- After three healthy versions and intervening failed attempts, verify current/previous healthy recoverability and the exact predecessor retention policy. Inject a crash before and after every snapshot deletion and replay it. Unknown files, wrong hashes/permissions, junctions, another installation, pending/repair journals and unsupported legacy sets must remain untouched. Exercise concurrent maintenance admission, receipt limits, and low disk; deferred cleanup must not reject or roll back a healthy installation.
- Race completed-download retirement and cancellation against a newer task for the same package and a different pending update. Unknown schemas, changed authorization/receipt, active task/download locks and partial files must prevent deletion. Verify interrupted exact-package deletion resumes safely without removing another task's pending record.
- Model updates require their separate opt-in plus an already installed, hash-verified/self-tested component. Verify signed compatibility, bounded ZIP inventory, old-pack retention, atomic pointer activation, consent withdrawal, concurrent offline import/removal, restart fallback, manual cache preservation and independent model/app rollback floors. Production quality must remain experimental regardless of repository fields.

## Required evidence

Retain hashes and machine/tool versions, structured outcomes, test logs and disposable-fixture screenshots locally. Do not include the user's supplied image or screenshots containing user pixels in source/evidence delivery archives. Record its SHA-256 and known false-negative score only. Native acceptance is complete only when the same candidate succeeds end to end; an unsigned EXE may still trigger Windows warnings, and those must not be bypassed.

Actual production provisioning is separate: approved compiled TUF root and publisher policy, signed release metadata, valid IP-SAN HTTPS for the configured address, reliable short-lived certificate renewal and operational recovery. None of that provisioning was performed during cloud implementation.
