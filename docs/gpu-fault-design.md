# Windows GPU 故障验证与处理设计（实现前）

## 用户场景

用户打开素材后驱动或图形设备不可用，界面不能依赖失效 GPU 才能说明发生了什么。原图必须保持只读；在途编辑/导出应取消，不能把未提交的副本当成成功导出。首版优先明确失败并允许重启应用打开原图；自动重建整个渲染器另行设计，不以 Surface 重建代替 Device 重建。

## 第一阶段：有界实证

只在显式自身 QA 参数下，使用官方 wgpu 30.0.1 Device::set_device_lost_callback 和 Device::destroy，销毁本应用的逻辑 device，记录回调原因及真实 eframe 后续行为。它不会改变系统驱动或其他应用，也不能代表真实硬件/驱动掉线。回调只保存诊断与唤醒信号，不显示阻塞弹窗、不持有 device 克隆，避免回调循环或死锁。另以空 backend 集合触发无可用 adapter 的初始化错误路径；记录错误和非零退出，正常模式继续采用 D3D12。

测试进程有最多30秒超时，监控者只终止自己启动的进程。每次检查输入文件完整 SHA-256 未变，随后重新启动正常 D3D12 图像窗口证明基本可恢复。故障测试不截屏上传，不自动点击系统对话框。若框架无法处理设备失效，记录准确问题后再决定失败处理方案，不宣称完整恢复已经实现。

## 第二阶段：依据结果加固

若设备故障导致默认 panic 或挂起，保留一份已验收的主程序作为回退，先设计主循环错误边界、后台取消和独立于GPU的错误通知。正常 shutdown 的 Destroyed 回调不误报；未知失效需去重，不继续提交GPU工作。调用方/渲染器无法安全重建时结束当前窗口，提示用户重启；不把失效视为普通图片错误而继续使用无效纹理。受控失效、错误边界和真实驱动事件分别列入验收，后者若不能执行继续明确未验收。

参考：[wgpu 30.0.1 Device](https://docs.rs/wgpu/30.0.1/wgpu/struct.Device.html)；[eframe 0.36.2 CreationContext](https://docs.rs/eframe/0.36.2/eframe/struct.CreationContext.html)。


## 实证后的最小修复设计

受控销毁已在本机观察到 Destroyed 回调后，egui-wgpu index staging buffer 在主线程panic，进程退出101（约1.4秒）；原图hash未变，正常重启D3D12成功。无可用backend返回诊断及退出1。先解决这个已观察到的错误，保持框架和纹理路径。

主循环包裹Result和panic错误边界，失败统一返回诊断与退出1；正常模式使用独立于GPU的系统错误对话框，显式QA只保存边界报告、不显示需要人工关闭的弹窗。panic仍保留原始日志，不能把“已捕获”误读为“没有panic”。ImageApp在Drop和正常退出均取消加载、编辑/导出、来源与预览任务，防止错误通知期间后台继续操作。新增真实Rust unwind取消测试和重复受控设备销毁/重启验证。该修复提供明确失败和重启路径，不自动重建Device，也不宣称真实驱动掉线或系统弹窗交互已验收。


受控失效修复后已观察到相同renderer panic由主循环捕获，退出1而不是未捕获101；原图不变，正常D3D12重启通过。再增加同一故障设计内的实际在途导出场景：显式QA工作流开始JPEG副本写入后延迟300ms销毁本逻辑device，检查Drop取消、JPEG目标未发布和原图hash不变。已完成的PNG副本可保留。后续 Debug 实测发现立即退出会遗留未发布的零字节临时文件，这是导出线程脱离所有权的竞态，不能仅因一次 Release 清理成功就判定通过。2026-10-09 的修正保留导出线程，在正常退出和捕获渲染 unwind 时先取消并 join，等待该线程释放其 NamedTempFile 后才返回主循环错误边界；不扫描目录或删除其他同前缀文件。硬终止、OS 文件操作阻塞和删除失败仍有独立边界，详见 [export-shutdown-fix.md](export-shutdown-fix.md)。当前新源码须在 Windows 重建并分别复测 Debug/Release。
