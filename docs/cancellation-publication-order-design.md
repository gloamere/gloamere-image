# 取消、结果应用与导出发布的先后规则（实现前）

用户点击取消时，后台成功结果可能已经入队，界面尚未应用。加载、编辑、来源检查和预览的同代结果在应用前还需检查对应令牌；取消后不应用像素、不加入撤销、不缓存核验、不显示旧预览。测试先取得真实加载线程的成功响应，保留而不应用，再取消并交给同一结果处理函数；编辑用真实成功通道排队后取消，验证原图/当前像素和历史未变。

导出具有不可逆的最终文件发布点，不能套用上述丢弃成功的规则。令牌使用共享原子状态：待处理、已取消、正在最终提交、提交结束。取消与提交均通过待处理状态的 compare-exchange 取得门控。取消先取得门控，最终发布函数不会运行；提交先取得门控，取消不阻塞界面、不撤销已获得的提交权，以文件系统提交的真实成功/错误为准。编码、同步、重读验证都在门控前，只有最终 persist_noclobber 在门控后。结束状态不把已发布副本重新标为取消，也不删除用户已收到的正确副本。

该顺序保证的是共享门控的可判定先后，而不是点击事件的物理时间，也不保证编码库中途抢占。每次导出使用独立令牌，最终提交最多一次。确定性回归覆盖取消先到而目标不存在、提交取得门控后另一线程取消而正确副本仍成功、导出成功入队后取消仍显示真实成功，以及已取消的加载/编辑成功不应用。保留原图和名称冲突防护，不能用取消修复覆盖策略。

## 共享令牌语义补充（实现前）

取消标记应保持通常的语义：调用 cancel 后，check 仍返回已取消，包括导出已经取得提交权之后。提交权和取消标记用同一原子值的不同位表示；门控先后不变，后到的取消只记录标记，不撤销已获得的最终提交权。发布函数不在门控后重新检查取消，返回真实文件系统结果；UI 对已发布成功不按取消标记丢弃。这样避免改变通用取消令牌在其他处理步骤中的含义。回归另验证成功导出后的取消仍能阻止同一令牌传入的后续编辑步骤。
