# Public-only compiled bootstrap addendum — 2026-10-10

This design precedes the scoped bootstrap implementation. It does not authorize generating production keys, installing a certificate, accepting a CA agreement, configuring a host or activating an update repository. The current candidate remains unconfigured.

A separately authorized source build may embed exactly two public files: `bootstrap/public-bundle.json` and `bootstrap/root.json`. The compiled source constant defaults to `None`; the reviewed build changes it explicitly to two `include_bytes!` references. No Cargo environment variable, runtime setting, network response, adjacent writable file or feature flag enables bootstrap. Public artifacts are authenticated by operator-reviewed source/build provenance and their out-of-band fingerprint; a self-signed root alone does not establish publisher identity.

The public manifest schema is version 1. Exact current pins are product `gloamere-image`, platform `windows-x64`, channel `stable`, origin `https://175.24.190.175`, and publisher policy `tuf-authenticated-unsigned`. It records `key_profile`, `root_version`, `root_length`, and lowercase `root_sha256`. No additional fields are accepted. The policy is fixed in code, not selected from this manifest. New origin/channel/publisher policies require another reviewed source change.

Supported new-key profiles are `root-2-of-3-six-keys` (recommended: three distinct root keys, threshold two; one distinct key each for targets/snapshot/timestamp) and `four-role-1-of-1` (one distinct key per role). Existing public roots must be reviewed for reuse first, rather than assuming keys do not exist. Roots outside these strict profiles require a separate reviewed compatibility decision, not silent key regeneration.

The signed root accepts public Ed25519 keys only, exact recognized TUF fields, unique map keys and disjoint role key sets; public key IDs must match the canonical key-object SHA-256. All referenced keys must exist, with no unused/aliased/private fields. Root version/length/digest must match the manifest; normal TUF root self-signature verification must pass. For fresh provisioning, signed issuance must not be future, expiry must be later than now and issuance, and lifetime must not exceed 366 days. A stale/corrupt/missing new bundle fails closed. Existing persisted state remains bound to its original root/configuration; this route must never silently reset it or replace a provisioned trust root. Root rotation uses the already-implemented consecutive old-and-new TUF authority path.

Lifecycle correction after review: fresh-provisioning validation rejects an expired root, but the private compiled-anchor path permits a historical anchor to have expired. It still validates the immutable byte/hash/profile/signature binding. The unchanged TUF verifier then validates the persisted chain or fetches consecutive roots with old-and-new authority and requires the final trusted root and metadata to be fresh before any target selection. Without a valid fresh rotation it fails closed. Root/metadata/release floors survive reopening, so an expired anchor cannot become a rollback or state-reset escape hatch. The historical anchor remains unchanged in the source and in the state configuration binding; copying another root or deleting state is not a supported migration.

The separate offline provisioner owns any later explicitly approved Windows key operation. Release-signing private keys remain in encrypted operator-controlled offline Windows storage, never in the source bundle, VPS, chat or Library. TLS/ACME private keys are different host credentials and need a separate approved host setup; no issuer/IP TLS setup script has been prepared by this core component. The unsigned-EXE policy still requires real TUF signatures and normal trusted HTTPS/IP SAN validation, preserves Windows prompts, and rejects a present invalid/unexpected Authenticode signature.

Tests use ephemeral keys only: default-off behavior, both valid profiles, wrong schema/pins/digest/length/version, duplicate or private fields, shared role keys, wrong thresholds, corrupted signatures and future/expired roots. No production bootstrap pair is created by these tests.
